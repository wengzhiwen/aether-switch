# AetherSwitch

**One machine. Many workloads. One command.**

A lightweight GPU mode orchestrator for local AI inference and generation. Switch a workstation between vLLM, a native inference engine, and an on-demand media workflow while keeping one shared lifecycle implementation.

[中文说明](README.zh-CN.md) · [Quick reference](中控使用说明.md) · [MIT license](LICENSE)

## What it manages

A mode is a prepared environment, model recipe and service. One mode exclusively owns the configured GPU pool, including when its API is idle and no model is resident.

- Check the target **before** interrupting the current mode.
- Stop the old systemd cgroup, including workers in separate sessions.
- Verify process identities, GPU compute PIDs and memory release.
- Start the target and wait for its application-specific readiness probe.
- Keep inputs, results and logs; never replay interrupted jobs.

Switching interrupts work immediately after preflight. Preparation, dependency installation, model downloads and builds are explicit steps. Services neither auto-restart nor restore a GPU mode after boot.

AetherSwitch is a single-operator Linux workstation tool. It does not route model API traffic, implement job scheduling, install frameworks or provide a multi-tenant security boundary.

## Requirements

- Linux, cgroup v2 and a working **user** systemd manager.
- Python 3.11+ at `/usr/bin/python3`; the controller itself has no pip dependencies.
- NVIDIA drivers and `nvidia-smi`; `findmnt`, Bash and systemd tools.
- `systemctl kill --kill-whom=all` and transient service properties used by the controller. The original deployment used systemd 259; other distributions need validation.

Frameworks use their own mode-local environments. API protocols, authentication, PP/TP, component placement and model tuning belong to modes.

## Set up a new checkout

Keep an existing deployment's `machine.toml` and `modes/` intact. For a new checkout:

```bash
cp -n examples/machine.toml machine.toml
# Edit mountpoint, filesystem UUID and GPU UUIDs for THIS machine.
nvidia-smi --query-gpu=uuid,name --format=csv
findmnt -M /your/model/mount -o UUID

mkdir -p modes
cp -Rn examples/modes/vllm-qwen36-35b-pp2 modes/
```

Follow that example's README to prepare its environment and existing local weights. Edit its paths, then set `enabled = true`. The model mount must be persistent and already mounted; AetherSwitch checks its UUID rather than mounting or modifying the host.

```bash
./mgr register vllm-qwen36-35b-pp2
./mgr check vllm
./mgr switch vllm
./mgr status
```

Examples are **disabled by default** and contain placeholder hardware identities. They are source-controlled recipes, not ready-to-run deployments.

## Commands

```bash
./mgr list
./mgr switch vllm           # Also accepts full mode IDs and configured aliases
./mgr switch strata
./mgr switch wan
./mgr status
./mgr status --json
./mgr stop                  # TERM; KILL remaining workers after 5 s by default
./mgr force-stop            # Immediate KILL of the owned cgroup, then verify release
./mgr restart wan
./mgr logs wan -f
```

Selecting the same healthy mode preserves the service, including a busy workflow node. `restart` explicitly interrupts and reloads. A target preflight failure preserves the old service; a startup failure cleans the attempted target and leaves the machine without a newly selected mode. Unknown processes are reported, never killed.

Each installed mode's `start.sh`, `status.sh`, `stop.sh`, `force-stop.sh` and internal `launch.sh` are symlinks to **one** project script. They are generated by `register`, not copied templates. A mode's `stop.sh` only targets that mode. Use `start.sh` for normal operation; `launch.sh` requires a controller-issued launch grant inside the expected unit.

## Three integration patterns

| Example | What it demonstrates |
| --- | --- |
| [vLLM / Qwen3.6 FP8 PP=2](examples/modes/vllm-qwen36-35b-pp2) | A standard inference command and OpenAI-compatible readiness |
| [Strata / Qwen3.8-Flash-Next](examples/modes/strata-qwen38-flash-next) | A native third-party engine, generated launch configuration, MTP and multi-GPU tuning |
| [Wan-Animate2 workflow node](examples/modes/comfyui-wan-animate2-rgba) | An authenticated resource API whose workers load models on demand as part of a larger workflow |

The third example is an adapter contract: supply your own worker/API and workflow. Private business code, transport bindings and upstream applications are not bundled.

## Repository boundaries

```text
server_manager/  scripts/  mgr     Shared orchestration; publish these
examples/                          Sanitized hardware and mode recipes
templates/                         Contract for new adapters
tests/                             CPU-only tests with temporary fixtures
machine.toml  modes/  .runtime/     Local operator data; ignored by Git
```

See [architecture and adapter contract](docs/controller.md), [deployment lessons](docs/deployment-notes.md), [testing and limits](docs/testing.md), and [contributing](CONTRIBUTING.md).

```bash
python3 -B -m unittest discover -s tests -v
python3 -B scripts/audit-public.py
```

Tests need no GPU, model weights, local configuration or user systemd service. The publication audit scans indexed Git content for deployment data and common identifiers/secrets; it is a guard, not proof that every possible secret is absent.
